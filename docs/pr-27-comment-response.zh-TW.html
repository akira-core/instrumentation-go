4. 建議 1:硬性 per-connection capability 未採納

最終決定:不採納。relay 在兩個方向都有權威是 0.8.0(revision 2)的核心設計,而 per-connection 的硬性 opt-out 會讓同一層出現第二種寫法 —— 那正是 D3 與 D14 花力氣移除的東西。硬關的手段維持在 process 層級:master veto、應用程式碼無法覆寫的模組環境變數、或乾脆不配置 relay。

已接受的代價,並已寫進文件:relay 搆得到的連線不論旗標值為何都會在每次操作付出評估成本。以下 4.1–4.3 保留當初的分析,作為日後若重啟討論的材料。
「o11y uses WithTracingEnabled(false) to mean hard-disabled/native-cost mode… An API such as WithTracingCapability(bool)… would allow effective = capability && master && dynamicModuleVerdict. When capability is false, the traced implementation should never be constructed or remotely enabled.」

4.1 現行行為驗證(flywindy 的描述完全正確)

  • WithTracingEnabled(false) 只是階梯的 option 層:module env var 或 relay 都能翻回 true(flags.go:215-228 的 ResolveLocal、階梯設計本意)。
  • 只要 relay 可能存在,tracedPossible() = relayPossible || … 為真 ⇒ traced 實作照建,每操作照付 2 次 evaluation——即使 option 明確給了 false(env_flags.go:86-88)。
  • 「hard-disabled / native-cost」契約在今日 API 下無法逐連線表達:唯一硬關是 process 級的 master env var,或乾脆不配置 relay——兩者都不是 per-connection 的。

4.2 深度分析:為什麼這不違反 0.8.0 的設計哲學

0.8.0 把 option 壓到 env 之下的三個理由(operator 可覆寫應用碼、堵 _oteltrace 繞道、階梯單調)全都是在防「應用碼把東西打開、operator 關不掉」。而 capability 是反方向的 clamp:

  • 它只能讓 tracing 更少,不能更多。capability=false 不可能造成 operator 不想要的 span 或 _oteltrace 寫入;operator 的一切「關」的權力(master veto、module env、relay disable)原封不動。0.7.0 的危害模式(option 蓋過 operator 的 off)在此結構上不可能重現。
  • 它不是階梯的第五層,不破壞單調性。它是階梯之外的 AND-clamp:effective = capability && ladder(…)——與 master veto 是 process 級 clamp 同構,capability 是 connection 級 clamp。
  • codebase 已有同一概念,只是不可設定。otel-gorilla-ws 的 capable(conn.go:97-102)正是「任何 OTel SDK 路徑是否可能執行」;WithTracingCapability(false) 等於讓呼叫端把 tracedPossible() 強制為 false。
  • 它順帶緩解發現 2:capability=false 的連線完全不經過 OpenFeature evaluation,無關 default provider 的成本與 key 碰撞風險就此隔離(process 級的根因仍要另修,見 §9)。

4.3 實作草案

// 四個模組各自新增(預設 true,向後相容):
func WithTracingCapability(v bool) Option

// gateState 加一欄:
type gateState struct {
    capability    bool   // 新增;option 未給時 true
    relayPossible bool
    masterLocal   bool
    tracingLocal  bool

func (g gateState) tracedPossible() bool {
    return g.capability && (g.relayPossible || (g.masterLocal && g.tracingLocal))
}

func (g gateState) tracing() bool {
    if !g.capability {            // 短路:零 evaluation、零配置
        return false
    }
    // …原邏輯不變
}
  • capability=false ⇒ direct 實作、noop tracer、mongo 連 shared.NewCommandMonitor 都不註冊(沿用現有 zero-cost 分支)、gorilla-ws 不 offer/confirm otel-ws。Mongo propagation 因 propagation = tracing && … 的 conjunction 自動歸零。
  • 不建議照單全收 WithTracingDefault 改名(對既有 WithTracingEnabled 是不必要的破壞;其語意本來就是「local 層的 desired state」)也不需要獨立的 WithRemoteEnableAllowed:兩顆旋鈕已完備——WithTracingEnabled 是階梯 rung(可被上層改),WithTracingCapability 是硬 clamp(誰都改不動)。三顆只會增加組合矩陣。

  • 時機:tag 前。API 形狀決策,downstream(o11y)採用 0.8.0 之前敲定成本最低;純增量、預設不變,對現有使用者零影響。

5. 建議 2:provider 所有權可注入 / GOFF adapter 拆分 維持現狀,補文件

最終決定:不拆分,也不承諾時程;改以文件補足。注入縫本來就存在而且不限廠牌 —— 任何 OpenFeature provider 綁到 FlagDomain,auto-install 就讓位。相依樹的抱怨屬實(D17 早已記錄為已知後果),但拆分要付出:zero-code 變成需要 blank import、release ordering 多一層、以及新增一個「忘記寫那行 import 就靜默沒有 relay」的失效模式。

已補的文件:feature-flags.md(en + zh-TW)新增 Embedding SDKs:自己擁有 provider 章節,寫明接管後初始化、evaluation context、logger、shutdown 全歸 embedder,且預設 provider 兩個方向都不受影響。
「The zero-code path installs a named OpenFeature provider and owns a process-lifetime poller, while every consumer inherits the GOFF/ANTLR/rules dependency tree. An injected gate/evaluator plus an optional GOFF adapter module would let embedding SDKs own initialization…」

5.1 兩個訴求要分開看

(a) 「所有權可注入」——縫其實已存在

OpenFeature named provider 本身就是注入點:應用(或 o11y 這類 embedding SDK)呼叫 openfeature.SetNamedProviderAndWait(otelflags.FlagDomain, p) 之後, auto-install 讓位(flags.go:425 的 stand-down 檢查),初始化、logger、shutdown、evaluation context、poll 週期全歸應用所有;provider 也不必是 GOFF——任何 OpenFeature provider 都行。這正是 docs/feature-flags.md「Installing your own provider instead」記載的路徑。所以「injectable」的訴求大半已被滿足,缺的是文件把「embedding SDK 完全接管」這個使用情境講清楚。

(b) 相依樹過重——屬實,且無法靠 linker 消除

otel-flags/go.mod 證實:GOFF contrib provider 拖入 ANTLR4、nikunjy/rules、jsonlogic、gcache、GOFF core、ofrep。因為 installProviderFromEnv 直接引用 gofeatureflag.NewProvider,dead-code elimination 救不了——每個只想要 wrapper 的下游都繼承整棵樹(binary 體積、依賴稽核、supply-chain 面積)。這個抱怨成立。

5.2 拆分方案與 zero-code 的正面衝突

把 auto-install 抽到選配模組(如 otel-flags/goff)後,core 只依賴輕量的 go-sdk。但 zero-code 路徑(「設環境變數,不改一行 Go」)是 0.8.0 文件的頭條賣點,而 lazy auto-install 住在 Resolver.evaluator() 裡才能做到 env-only 啟用。拆出去後 zero-code 至少要求一行 blank import:

import _ "github.com/akira-core/instrumentation-go/otel-flags/goff"

權衡:

立場:0.8.0 維持現狀(zero-code 是既定設計支柱,tag 在即),但把「拆分 GOFF adapter 至選配子模組」列為 0.9 的正式計畫並回覆 flywindy 此排程;同時在 docs 補「embedding SDK 接管 provider」章節(即刻可做)。SetEvaluator 式旁路除非 o11y 提出 evaluation pipeline 成本實測上的必要,否則先不加——兩條真相來源是長期維護負債。

6. 建議 3:明確 targeting context / service identity 只補文件

最終決定:不改程式碼(OTEL_RESOURCE_ATTRIBUTES fallback 與 SetTargetingAttributes 都未採納),只補文件。

關鍵事實(已驗證 go.opentelemetry.io/otel/sdk@v1.44.0):resource/env.go:39-40 只有 os.Getenv,非測試碼中 os.Setenv 零出現 —— SDK 從不回寫環境;而 sdk/trace.TracerProvider 只導出 Tracer / RegisterSpanProcessor / UnregisterSpanProcessor / ForceFlush / Shutdown,沒有 Resource()。所以程式化設定的 service.name 在設計上就到不了我們手上,這不是改我們的碼補得起來的缺口 —— 值必須由呼叫端主動交付。

文件已寫明兩條今天就能用的交付路徑:自有 provider 時設 API 級全域 evaluation context(D12 保證我們不覆寫);走 zero-code 時在 Init 裡「未設才設」OTEL_SERVICE_NAME。
「o11y configures service.name in its OTel Resource, not necessarily through OTEL_SERVICE_NAME; requiring both creates configuration drift.」

現況

  • service.name targeting 屬性只在 auto-install 路徑、只從 OTEL_SERVICE_NAME 讀(flags.go:460-465),per-invocation 傳遞、刻意不碰全域 context。
  • 程式內以 WithServiceName("checkout-api") 設 Resource 的應用,env var 沒同步就 drift——relay 的 service.name targeting 規則對它靜默失效。抱怨成立。

分析與對策(由便宜到重)

  1. 補讀 OTEL_RESOURCE_ATTRIBUTES(建議採納,tag 前):OTel 規範標準變數,格式 service.name=checkout-api,…。OTEL_SERVICE_NAME 未設時 fallback 解析之,與 SDK Resource 偵測順序一致。約十行 + 測試,消除大部分 drift 場景(多數部署兩者至少設其一)。
  2. 文件補「自有 provider 路徑的 targeting」(即刻):應用擁有 provider 時,本 library 對 evaluation context 完全不插手(flags.go:302-305,evalCtx 保持零值),所以 API 級全域 context——openfeature.SetEvaluationContext(NewTargetlessEvaluationContext(map[string]any{"service.name": …}))——今天就會合流進每次評估。o11y 型 SDK 已可程式化提供 identity,只是沒人告訴它。
  3. 程式化 setter(otelflags.SetTargetingAttributes(map[string]any))暫緩:只有在「用 auto-install、又不能設任何 env var、又要程式化 identity」三條件同時成立時才有需求——這組合罕見(能改程式碼就能裝自己的 provider)。等真實需求再加,避免 API 面積膨脹。

8. 發現 1:remote disable 不跨重啟延續 部分接受

「OTEL_NATS_TRACING_ENABLED=true + relay otel-nats-tracing=false,AP restarts → before the first fetch, local=true is used → tracing is briefly enabled again… Could provider-not-ready default to disabled, or could the auto-install path offer a wait-for-ready policy?」

8.1 場景核實

屬實。auto-install 非阻塞(flags.go:450 的 SetNamedProvider),首次成功 fetch 前 Client.Boolean 一律回傳 local——此例 local=true,故重啟後短暫(通常為一次 HTTP RTT;relay 不可達時無上限)重新開啟。文件「The startup window」的敘述(「window 可延遲 relay 驅動的 enable,永不引入 enable」)沒有說謊,但它只涵蓋 relay 方向;local=on、relay=off 這一象限——正是把 relay 當 incident brake 的象限——被留白了。

8.2 「provider-not-ready ⇒ disabled」必須拒絕

把 not-ready 讀成 false 是逐 key 生效的,而 master key 的 default 是 true、語意是 veto:

  • 每個配置了 relay 的 process,每次重啟都會被 master key 的 not-ready ⇒ false 全面 veto,直到首次 fetch——把「短暫多 trace」換成「整艦隊短暫全黑」,而且 relay 停機時無限期全黑。這正是文件「The relay is not a startup dependency」明文拒絕的形態:control plane 變成 availability dependency。
  • 它摧毀階梯的核心不變量——「relay 沉默與 relay 失敗刻意不可分,兩者都表示下一層決定」(flags.go:20-25)。not-ready 一旦是一種「意見」,每一層的推理都要重寫。
  • 它也違反單調性:一個「沒有資料」的來源憑空覆蓋了 deployment 明確寫下的 env=true。

8.3 接受的三件事

  1. 明文記載(tag 前必做):在「The startup window」加反方向段落:remote disable 不跨重啟延續;relay 是 runtime 控制面,持久狀態屬於環境變數。Incident-brake 正確操作程序:先翻 relay 止血(秒級生效),隨後把 env var 落進 deployment,重啟前完成——之後 relay 值與 env 一致,window 無害。
  2. Regression test(tag 前必做):釘住「首次 fetch 前 local 勝出」語意(裝一個永不 ready 的 provider,驗證 local 值被使用)——這是行為契約,值得測試保護,也是 flywindy 的最低要求。
  3. Opt-in 等待策略(接受,可 0.8.x 追加):新增 OTEL_INSTRUMENTATION_GO_FLAGS_STARTUP_WAIT=<duration>——設定時 auto-install 改用阻塞式安裝,以該值為逾時上限;逾時則照舊以 local 繼續並 slog.Warn。預設仍非阻塞,不把 relay RTT 塞進所有人的第一個操作。另外,自有 provider + SetNamedProviderAndWait 今天就能關閉 window——文件已暗示,改正函式名後明示(見 §7)。

9. 發現 2:無關 default provider 觸發 RelayPossible() 確認屬實,接受

「openfeature.SetProvider(businessProvider) // application feature flags only … is enough to make RelayPossible() true… Please consider requiring a provider explicitly bound to otelflags.FlagDomain, and add a default-provider-only test.」

9.1 程式碼證實 + 一個留言沒點到的更糟側面

  • flags.go:278:NamedProviderMetadata(FlagDomain) 在 domain 無綁定時 fallback 到 default provider 的 metadata ⇒ 只設過 SetProvider(businessProvider) 的應用讓 RelayPossible() 為真 ⇒ traced 實作建起、每操作 2 次 evaluation 打進業務 provider(mongo 寫入 3 次)、外加 mongo CommandMonitor 註冊。key 若碰撞(otel-nats-tracing 等)還會誤翻 instrumentation。全數屬實。
  • 加碼發現:同一個 fallback 讓 auto-install 錯誤讓位。flags.go:425 的 stand-down 檢查用同一呼叫:當 operator 明確設了 OTEL_INSTRUMENTATION_GO_FLAGS_ENDPOINT、而應用恰好有無關的 default provider 時,讀回非 NoopProvider ⇒ GOFF provider 不安裝,instrumentation key 全打到業務 provider(大概率 FLAG_NOT_FOUND ⇒ 永遠 local)。結果:operator 的 endpoint 靜默失效,relay 控制面整個不存在——比「多付評估成本」嚴重。修 RelayPossible 時必須一併修這裡。

9.2 修復方向與實作難點

目標語意:「relay 可能」= endpoint 已設,或 FlagDomain 上明確綁定了 named provider;default provider 的存在不算數。難點:go-sdk 的 NamedProviderMetadata 是唯一查詢入口且必 fallback,缺一個無 fallback 的「此 domain 是否有綁定」查詢。名字比對(NamedProviderMetadata(FlagDomain).Name != ProviderMetadata().Name)有假陰性:應用同時把 GOFF 綁 default(業務)與 named(instrumentation)時兩邊 metadata 名相同,會誤判為未綁定。可行組合:

  1. 新增 otelflags.InstallProvider(p) error(包裝 SetNamedProviderAndWait(FlagDomain, p) + 記錄 package 級「已明確綁定」bool),文件改為推薦入口。RelayPossible = endpoint 已設 || autoInstallDone || explicitInstall——對走新入口與 zero-code 的使用者精確。
  2. 對直接呼叫 raw openfeature.SetNamedProviderAndWait 的既有模式(目前文件教的),保留 metadata 啟發式當 best-effort 相容層,並記載邊角:同名 provider 同時綁 default 時請改用 InstallProvider。0.8.0 尚未 tag,現在改推薦入口零成本——這是此建議應排進 tag 前的主因。
  3. 照 flywindy 要求補 default-provider-only regression test:只設 default 業務 provider 時,RelayPossible()==false、direct 實作、零 evaluation。
  4. 順手向上游 go-sdk 提「無 fallback 的 named-binding 查詢」feature request,長期消滅啟發式。

補充:§4 的 capability option 給了受影響下游即刻的逐連線逃生門,但 process 級根因仍需本節修復——兩者互補,不互相取代。

12. 英文回覆(依最終立場改寫,可直接張貼)

此草稿反映上述所有最終決定,並描述已完成的改動。張貼前請確認 v0.8.0 尚未 tag。

Thanks — this is the most useful review this change has had, and it found a real bug. We held the v0.8.0 tag to land the fixes. Point by point, including the two asks we are declining and why.

**Finding 2 (unrelated default provider activates the dynamic path) — confirmed, fixed, and it was worse than you described.**

`NamedProviderMetadata(domain)` falls back to the *default* provider's metadata when nothing is bound to the domain (go-sdk v1.17.2, `openfeature_api.go:174-184`), and we were reading it as "is a provider bound to our domain". Your case — a business provider in the default slot making `RelayPossible()` true — is exactly right. The second half we had not seen: the auto-install used the same check, so with `OTEL_INSTRUMENTATION_GO_FLAGS_ENDPOINT` **set** and an unrelated default provider present, we stood down, installed nothing, and every instrumentation key then fell through to the business provider via `ForEvaluation`. The operator's relay was silently inert. That is the more serious direction, and it is on the path where someone explicitly asked for a relay.

Fixed by one predicate now used by both call sites: an explicit-install record first, then a metadata comparison that rejects an answer merely echoing the default. Also added `otelflags.InstallProvider(p)` — `SetNamedProviderAndWait(FlagDomain, p)` plus that record — as the recommended install path; raw `SetNamedProviderAndWait` stays supported through the heuristic. Because it waits, it also closes the startup window.

We deliberately did *not* use `GetNamedProviders()`, which would answer exactly: it returns the live map without copying (`openfeature_api.go:187-192`), so reading the result races a concurrent `SetNamedProvider` and can take the process down with `concurrent map read and map write`. A library cannot buy exactness at that price. The one residual false negative — the same provider *name* bound to both slots — is what `InstallProvider` closes. We will raise both points upstream.

Tests added: the comparison's full truth table (the fallback row cannot be built through the SDK, since a domain cannot be unbound once bound, so the comparison is a separate function), `RelayPossible()` false with a default provider only, the auto-install proceeding when only a default provider exists, and `InstallProvider` outranking the heuristic.

**Finding 1 (remote disable is not continuous across restart) — accepted as a documentation and test gap; the mechanism stays.**

Your scenario is real and is now stated in the docs instead of being left to be discovered. We are declining "provider-not-ready ⇒ disabled": it applies per key, and the master key's local default is `true`, so every restart of every relay-configured process would be fully vetoed until its first fetch — and would stay dark for the duration of a relay outage. That makes the control plane an availability dependency, which our own spec forbids, and it lets a source with no data outrank one the deployment wrote down.

What we did instead: the docs now say plainly that a relay `false` does not survive a restart, that the relay is runtime control while durable state belongs in the environment variable, and that the incident-brake procedure is flip-the-relay-then-land-the-variable before anything restarts. A regression test pins that a bound-but-not-ready provider leaves the local value in charge in both directions, including that it cannot veto the master. We also did not add the opt-in wait knob — `InstallProvider` already gives you a blocking install if you want the relay's answer before your first operation.

**4. Full runtime effect — accepted, all three.** New section covering: turning a module off stops trace-context injection and extraction as well as spans, so distributed traces break at that boundary; a relay-driven enable changes the code path and its cost but cannot export anything through a no-op TracerProvider — enabling instrumentation and enabling export are separate decisions and the relay only makes the first; and the master flag governs this repository's modules only, not an embedding SDK's provider, its other integrations, or your export pipeline. Both languages.

**3. Targeting identity — documented, no new API, and the reason matters.** You are right about the drift, and it is not fixable from our side. OpenTelemetry builds the Resource *from* the environment and never writes back (`sdk/resource/env.go` reads only), and neither `trace.TracerProvider` nor `sdktrace.TracerProvider` exposes a Resource accessor. So a `service.name` set in Go code is invisible to any third-party library by construction — it has to be handed over. Two routes now documented: when you own the provider, set an API-level global evaluation context and it reaches every evaluation we make (we pass an empty invocation context on that path and never override you); on the zero-code path, set `OTEL_SERVICE_NAME` from the same value if it is absent. We would rather point at those than add a setter that only helps the narrow case of auto-install plus no writable environment.

**2. Provider ownership and the dependency tree — the seam exists; the split is declined for now.** Ownership is already yours and is not GOFF-specific: bind any OpenFeature provider to `FlagDomain` (now via `InstallProvider`) and the auto-install stands down — initialisation, evaluation context, logger and shutdown are yours, and we never call Shutdown on a provider we did not install. There is a new *Embedding SDKs* section spelling this out, including that your default provider is untouched in both directions.

The dependency-tree complaint is legitimate and we have it recorded as a known consequence: ANTLR, rules and jsonlogic reach every consumer and the linker cannot drop them. We are not splitting it into an optional module in 0.8.0 and are not promising a date. The reason is not that we disagree about the cost — it is that the split trades the zero-code path for a blank import, adds a third stage to an already two-stage release ordering, and creates a new silent-failure mode when that import is forgotten, which is the same class of bug as Finding 2. If it happens it should be designed properly, not rushed alongside a bug fix.

**1. Hard per-connection capability — declined.**

We understand the contract you want and we are not going to add it. Bidirectional relay control is the core of this release, and a per-connection setting that no relay value can lift reintroduces a second spelling of one tier — precisely what this change removed when it made the option lose to its environment variable and deleted the config-conflict sentinels. Two rungs meaning "off" with different override semantics is the shape that generated the "I set the flag and nothing happened" reports we were fixing.

The hard-disable escapes we support are process-scoped and we think they cover the deployment case: `OTEL_INSTRUMENTATION_GO_TRACING_ENABLED=false` stops everything regardless of any relay value; `OTEL__TRACING_ENABLED=false` stops one module and application code cannot override it; and a process with no endpoint and no provider bound to `FlagDomain` — which, after the Finding 2 fix, now correctly excludes a business provider in the default slot — never touches the OpenFeature SDK at all and keeps the pre-dynamic cost profile exactly.

What we owe you is honesty about the cost we are keeping, and it is now documented rather than implied: **a relay-reachable connection evaluates on every operation whatever the flag's value.** `WithTracingEnabled(false)` means "resting state off, relay may change it", not "never traced, native cost". If that is load-bearing for your AP-facing contract, the supported way to express it today is not to configure a relay for those processes.

**Finding 3 (benchmarks) — accepted as a documentation defect, fixed by deleting the claim rather than by adding code.** You are right that `2 µs / 336 B / 7 allocations` is not reproducible from this repository, and "recorded rather than assumed" was not a claim we could stand behind. Both are gone, replaced by an order-of-magnitude statement and an instruction to measure on your own workload. The per-operation evaluation counts stay, since those are a property of the design rather than of a machine, and we added the sentence that was missing: the cost is paid whatever the flag's value.

Detailed analysis, including the truth tables and the SDK source references: `docs/pr-27-comment-response.zh-TW.html`; design rationale in `openspec/changes/openfeature-dynamic-flags/design.md` (D22 and § Downstream feedback).
