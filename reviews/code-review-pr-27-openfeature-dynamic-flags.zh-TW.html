範圍與變更摘要

本 PR 將 MongoDB、NATS／JetStream 與 gorilla/websocket 的 tracing／propagation 開關改為透過 OpenFeature relay 在執行期解析，並以一秒 TTL 的 Resolver snapshot 取代永久快取的 Gate。連線級 WithTracingEnabled 保持靜態且最高優先； 全域環境變數 OTEL_INSTRUMENTATION_GO_TRACING_ENABLED 是 relay 無法覆寫的 kill switch。

  • MongoDB v1/v2（0.9.0 / 2.9.0）：Collection、Cursor、ChangeStream 改為 direct/traced 雙實作，逐操作選擇；SingleResult 例外固定實作。
  • NATS／JetStream（0.8.0）：subscription、Consume、Messages iterator 改為逐訊息解析；oteljetstream.New() 永遠回傳 traced wrapper。
  • WebSocket（0.8.0）：分離 capable（靜態）、tracingEnabled（協商結果）、featureEnabled()（動態 span gate）。
  • 規格／文件：OpenSpec openfeature-dynamic-flags、四模組 CHANGELOG、根目錄 README／CLAUDE.md。

適用的 repository 指引只有根目錄 CLAUDE.md。 依 code-review 指令，本次未執行 build、test 或 typecheck；CI／編譯器可捕捉的問題不列為審查發現。

正式發現：NewConn 在 module/relay 關閉時仍改寫 wire payload

未協商 otel-ws 的普通 peer 會收到 envelope，而不是原始應用訊息。

高嚴重度 · 85/100

標記原因

bug（相對於 0.7.x 的 regression）+ CHANGELOG／design 宣稱被違反。

位置（full SHA）

  • otel-gorilla-ws/conn.go#L93-L100 — NewConn 固定傳入 tracingEnabled=true。
  • otel-gorilla-ws/options.go#L78-L91 — effectiveCapability 只看 override 或全域 kill switch，刻意不看 relay／module env。
  • otel-gorilla-ws/conn.go#L119-L164 — capable 為真且 tracingEnabled 為真時，feature 關閉只停止 span／header，仍呼叫 marshalWire。

可重現情境

  1. 應用自行完成 WebSocket handshake，再用 NewConn(rawConn) 包裝連線。
  2. 設定 OTEL_INSTRUMENTATION_GO_TRACING_ENABLED=true，但 module env／relay otel-gorilla-ws-tracing 為 false。
  3. effectiveCapability → true；NewConn 把 tracingEnabled 固定為 true。
  4. WriteMessage 解析到 feature=false：不建立 span、不注入 header，但仍將資料包成 JSON envelope。
  5. 未使用此 wrapper、也未協商 otel-ws 的 peer 原應收到 hello／{"x":1}，實際收到 {"header":{},"data":...}。
獨立 repro（評分 agent）： global on + OTEL_GORILLA_WS_TRACING_ENABLED=false + relay off + NewConn → plain gorilla server 端收到 {"header":{},"data":"hello"}，而非 hello。

為何不是 intentional breaking

  • CHANGELOG 0.8.0 明寫：兩端皆用此 library 且 global on 時，dynamic off 仍交換 envelope——這針對 已協商 otel-ws 的路徑（Dial／Upgrade）。
  • 同段亦寫：「Peers that do not negotiate otel-ws — including all non-library clients — see no change on the wire。」
  • NewConn 不經 handshake、卻強制 tracingEnabled=true，在 global on + module off 時仍 envelope，直接違反上述保證。
  • 0.7.x 在 feature off 時 WriteMessage 開頭即 raw passthrough；即使 NewConn 設了 tracingEnabled=true 也不會改寫 wire。本 PR 的 capable／tracingEnabled／feature 三層拆分引入 regression。

影響

  • 應用層 payload 被透明改寫；非 instrumented peer 無法取得預期資料。
  • 即使未安裝 OpenFeature provider，只要使用 global-on／module-off 的環境變數組合同樣觸發——與「無 provider 時行為與前一版本相同」承諾衝突。
  • 問題發生在 wire format 邊界，無法靠下游 tracing 設定補救。

測試缺口

TestIncapableConnStaysRawPassthrough 只覆蓋 global off。 dynamic flag 測試用 NewConn 時多半只 assert span 數量，未 assert peer 收到的 raw bytes。 缺少 global on + module/relay off + NewConn + raw peer 的 payload regression。

建議修正

不要把「NewConn 歷史上預設可 tracing」等同於「peer 已協商 otel-ws」。可行方向：

  1. NewConn 在無法證明協商成功時，envelope 決策應跟隨有效 feature（或單獨的 negotiated 旗標），feature off 時 raw passthrough；或
  2. 若契約確定改為 NewConn 永遠 envelope，必須在 CHANGELOG／README 明確標為 wire-format breaking，並更新「non-negotiating peers see no change」的宣稱。

並新增上述組合的 peer-payload 測試。

近門檻：MessageBatch 只在 Fetch 建立時解析動態旗標

既有 batch 在 relay 切換後仍固定為 direct 或 traced。

Agent #1（CLAUDE.md）+ Agent #5（OpenSpec）。評分 75 —— 不進入正式 PR comment，但強烈建議修復。

位置

雙向失敗

建立時Relay 後續預期實際

建議修正

永遠回傳可動態 dispatch 的 batch wrapper；forwarder 每則訊息重查 connection tracing gate。 關閉時完全略過 tracer／attributes／propagator。補同一 batch 上 true→false／false→true 測試 （對齊既有 Consume／Messages 動態測試）。

已排除的候選問題

1. Mongo refresh() 兩次獨立 Boolean 評估

flags.go#L167-L178 （v2 同文）在同一次 refresh 內依序呼叫 client.Boolean。若 relay 恰在兩次呼叫間翻轉， snapshot 可能寫入 relay 從未同時存在的組合（例如 (true,true)）。

50/100 · 排除

技術上成立，且與「同一 snapshot instant、不會 torn read」的註解／CLAUDE.md 宣稱不完全吻合。 但 resolveDocumentPropagation 會擋住最危險的 tracing-off＋propagation-on 有效路徑； 觸發窗口極窄（微秒級 Boolean 間隙）、錯誤狀態最多快取約 1 秒，屬短暫 telemetry 不一致而非高頻功能缺陷。

2. TTL 邊界跨兩次 Enabled() 的 Mongo torn read

env_flags.go#L86-L108 中 mongoTracingEnabled() 與 mongoPropagationResolved() 分兩次 Enabled()。並發 refresh theoretically 可造成 stale tracing=true 搭配 fresh propagation=true。

第二輪審查（8 面向 × 5 agent，見下方 「近門檻：單一呼叫鏈 Mongo torn read」）找到比「需要並發 refresh 競爭」更容易觸發的具體路徑—— 同一 goroutine、同一次操作內，Collection.impl() 與 traced.Collection 內部的 propagationOn() 各自獨立呼叫一次 effectiveTracing()，兩次讀取之間只要跨過 1 秒 TTL（例如一次較慢的查詢）即可分屬不同 snapshot。 機制本質相同，但不再需要「並發」這個前提，信心由 45 上修為 60，移至近門檻章節、不再列為排除項。

中高嚴重度 · 60/100 · 未達正式門檻

標記來源

5 個角度中有 4 個（逐行 scan、removed-behavior auditor、cross-file tracer、efficiency）各自獨立收斂到同一叢集， 經覆核程式碼確認呼叫鏈真實存在。

呼叫鏈（已覆核，v1／v2 皆同構）

  1. Collection.impl()（collection.go#L35-L40） 呼叫 c.tracing()（即 Database.effectiveTracing / Client.effectiveTracing， database.go#L28-L36） →第一次 mongoResolver.Enabled(idxTracing)，決定走 traced 還是 direct。
  2. 選中 traced 後，實際 CRUD（如 FindOne 的網路往返）執行期間呼叫 t.propagationOn() → PropagationEnabled（即 Client/Database.effectivePropagation， client.go#L65-L73 / database.go#L41-L49） → resolveDocumentPropagation(d.effectiveTracing(), ...) （env_flags.go#L104-L109） → 第二次、獨立的 mongoResolver.Enabled(idxTracing) 呼叫。
  3. internal/flags/flags.go 的 Enabled(i) 每次呼叫都獨立檢查 r.now().Sub(s.at) >= r.ttl；一旦第 1、2 步之間的耗時（例如較慢的 MongoDB 查詢、GC pause、relay 輪詢延遲）超過 1 秒， 第二次呼叫會觸發自己的 refresh()，讀到與第一次不同的 snapshot——正是 env_flags.go#L21-L23 註解宣稱「不會發生」的 torn read，且完全發生在單一 goroutine、單一操作內——不需要並發 refresh。

可觀察的不一致

因為 resolveDocumentPropagation 在 tracingEnabled 為 false 時立刻回傳 false，不會產生 「tracing off + propagation on」這種矛盾組合——本身仍是 fail-safe 的。但會產生另一種不一致：第 1 步讀到 tracing=true， 因此已經選了 traced 實作、span 已經建立；relay 剛好在第 2 步之前把 tracing 切成 false， 第二次 effectiveTracing() 讀到 false，resolveDocumentPropagation 直接回傳 false，propagation 被關閉。 結果是：span 依第 1 步的舊決定被建立並送出，但 _oteltrace 依第 2 步的新決定不被寫入——同一次操作的 span 與 propagation 決策不再對應同一個 relay 瞬間，與 CLAUDE.md／程式碼註解宣稱的單一 snapshot 保證相違。

為何只給 60（非 ≥80）

  • 觸發窗口仍需操作耗時恰好跨過 1 秒 TTL 邊界，多數 CRUD 呼叫遠快於此；主要風險場景是慢查詢、鎖等待或 relay 本身回應緩慢。
  • 失敗方向是 fail-safe（只會少寫 _oteltrace，不會產生「tracing off 卻仍 propagate」的更危險組合）。
  • 不影響資料正確性，只影響同一操作的 span／propagation 決策是否來自同一 relay 瞬間——可觀測性不一致而非功能性 bug。

機制（verifier 已逐行確認）

  1. Enabled()（flags.go#L151-L160） 在 snapshot 為 nil 或過期時直接呼叫 refresh()——沒有 mutex、沒有 singleflight，任意多個 goroutine 可同時進入。
  2. refresh()（flags.go#L162-L184） 的 at: r.now()（L181）在整個評估迴圈跑完後、store 前一刻才取——時間戳反映的是「完成時間」，不是「向 relay 讀值的時間」。 寫入是無條件 r.snap.Store(s)（L182），無 CAS、無 generation 檢查。
  3. Goroutine A 先開始、先向 relay 讀到舊值（例如 false），但因 GC／scheduler／網路抖動較晚完成； Goroutine B 後開始、讀到 relay 翻轉後的新值（true）、先完成並 store。 A 隨後以更晚的時間戳無條件蓋掉 B——resolver 現在回報 stale 的 false， 且 r.now().Sub(s.at) >= r.ttl 檢查把這份 stale snapshot 當成新鮮的，最多再服務整整 1 秒。
  4. 程式碼註解（L164-L166）明寫「Concurrent refreshes are deliberately not serialized: evaluation is idempotent, the last store wins」—— 作者知道 refresh 不序列化，但「evaluation is idempotent」的前提在 relay 值於兩個 refresh 之間翻轉時不成立； 「時間戳在 store 時才蓋章導致 stale 值看起來新鮮」這一層後果註解並未涵蓋。

為何給 70（非 ≥80）

  • 需要兩個 refresh 恰好重疊且完成順序與讀取順序相反——高 QPS 服務在 TTL 邊界或啟動時（snapshot 為 nil，所有首批請求同時 refresh）確實會發生，但窗口仍窄。
  • 後果是旗標翻轉的生效延遲從最多 1 秒變成最多約 2 秒、且中間短暫回退舊值——telemetry 開關的短暫延遲，不是資料正確性問題。下一輪 refresh 即自癒。
  • 與已知的「refresh 內兩次 Boolean 組成 torn pair」（第一輪排除項，50）同屬 refresh 併發語意，但機制獨立：那是單次 refresh 內部的組合問題，這是兩次 refresh 之間的覆寫順序問題。

建議修正

任一即可：(1) 在評估開始前取 at（時間戳反映讀值時刻，stale 覆寫者會立刻再被視為過期）； (2) CompareAndSwap + 保留舊 snapshot 指標做 generation 檢查，舊 generation 的 store 直接放棄； (3) singleflight／mutex 序列化 refresh（註解已權衡過鎖成本，但 (1) 幾乎零成本即可消除「stale 看起來新鮮」的最壞情況）。

發布阻斷 · 已修

為了共用測試 helper，本輪把 boolFlag／relayFlag／setRelay 抽到新的 otel-testkit/ofrelay 套件，並讓四個模組的 dynamic_flags_test.go import 它。 代價是四個 已發布模組的 go.mod 各被加入： 

require github.com/akira-core/instrumentation-go/otel-testkit v0.0.0

replace github.com/akira-core/instrumentation-go/otel-testkit => ../otel-testkit
replace github.com/akira-core/instrumentation-go/otel-sampler => ../otel-sampler

Go 的 replace 指令只在 main module 生效，被當成依賴時完全忽略； 而 otel-testkit 依 CLAUDE.md 是「deliberately untagged」（git tag | grep testkit 無結果）， v0.0.0 並不存在。因此下游只會拿到一個無法解析的 requirement。

實測復現（暫時 main module，僅 replace otel-mongo 到本機，模擬消費者）： 
$ go mod tidy
go: downloading github.com/akira-core/instrumentation-go/otel-testkit v0.0.0
go: example.com/consumer imports
        github.com/akira-core/instrumentation-go/otel-mongo/otelmongo tested by
        github.com/akira-core/instrumentation-go/otel-mongo/otelmongo.test imports
        github.com/akira-core/instrumentation-go/otel-testkit/ofrelay: module lookup disabled

注意 go build 因 module graph pruning 仍可通過——這正是危險之處： CI 的 test-and-lint（在 module 目錄內、replace 生效）完全不會發現， 問題只在下游使用者 go mod tidy／go mod download all／vendor 時才爆。 tidy 會納入「已 import 套件的測試依賴」，所以即使消費者只用非測試程式碼也一樣受害。

另有兩個附帶代價：otel-testkit 會把 testcontainers-go／Docker 整條依賴樹帶進已發布模組的 module graph； 且 ofrelay/relay.go 是非測試檔案卻 import testing 與 testify/require。

已套用修正：回復四個模組的 go.mod／go.sum（git checkout）、刪除 otel-testkit/ofrelay/、把 helper 還原成各模組測試檔內的本地函式，並在每處加上註解說明 「為何刻意重複而非抽取」——與 internal/flags 的 byte-identical vendoring 同一理由： 模組獨立發布，不能為了共用測試 helper 在已發布 go.mod 留下無法解析的 requirement。 修正後同一消費者實驗 go mod tidy 通過。
